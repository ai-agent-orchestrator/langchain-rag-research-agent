# R6 — 찬반·조건 검색 병렬 분기 옵션

## 무엇을 고쳤나

`ResearchConfig.parallel_branches: bool = False`를 마지막 필드에 추가했다. 기본값은 기존 순차 `retrieve` 노드와 간선, 검색 호출 순서·개수·인자를 유지한다. 새 모듈·의존성은 없다.

켜면 LangGraph의 여러 노드 fan-out과 명시적 합류 간선을 사용한다. `stance_split=False`이면 base만 실행한다.

```text
순차: plan -> retrieve(base -> pro -> con -> limits) -> refine -> extract -> ...
병렬: plan -> [retrieve_base, retrieve_pro, retrieve_con, retrieve_limits]
           -> join_retrieval -> refine -> extract -> ...
```

각 검색은 별도 노드에서 실행한다. `branch_hits`의 추가 리듀서는 순위 후보를 모으고, 모든 갈래가 끝난 뒤 합류 노드가 base→pro→con→limits 순서로 갈래당 k개를 선택한다. 선택 출처는 기존 `sources` 리듀서 `_merge_sources`로 병합되므로 source_id 중복은 하나만 남고 먼저 선택한 갈래의 본문·메타데이터가 우선한다. `pending`은 합류에서 한 번 작성하므로 병렬 쓰기 충돌 없이 기존 refine/extract 경로를 사용한다. gap 재검색과 rewrite 루프는 기존 경로다.

순차 경로는 앞 갈래의 출처 수만큼 다음 검색량을 늘린다. 단순히 모든 갈래에서 k개만 받으면 중복이 많은 자료에서 출처가 줄어든다. 이를 막기 위해 병렬 갈래 i(0부터)는 `k*(i+1)+기존 출처 수`개를 요청한다. 합류에서는 당시 순차 요청량 `k+선행 고유 출처 수`까지만 후보를 사용하고 기존 출처를 제외한다. 완료 순서가 보고서의 문장 선택 순서에 영향을 주지 않는다.

동등성 조건은 검색기가 결정적이고, 같은 쿼리에서 요청량을 늘렸을 때 기존 순위가 같은 접두사로 유지되는 top-k 계약이다. 검색기는 동시 호출에도 안전해야 한다. 요청량에 따라 순위를 바꾸거나 공유 상태를 변경하는 임의의 `SearchFn`에는 동등성을 주장하지 않는다. 옵션 주석에도 이 조건을 명시했다.

## 시험

새 `tests/test_research_parallel.py`에 합성 자료 경로 시험 21건을 작성했다. 실제 `ResearchRunner`, 컴파일된 LangGraph, 기존 `keyword_search`와 데이터 클래스를 사용한다. 합성 검색 함수는 겹치는 순위·동시 실행·예외를 입력하기 위한 SearchFn이며 그래프·리듀서를 가짜 구현으로 대체하지 않는다.

- 순차/병렬 출처·claim 집합과 순서, 보고서·draft·계획·metrics·검수 코드·중단 상태·log·shadow cost 동등성: k=1/2/8, stance 분리와 gap 루프 on/off 조합 12건. injection 본문이 claim에서 제외되는지도 확인한다.
- 모든 갈래의 검색 순위가 겹쳐도 각 갈래 quota를 채우고 출처 8개만 남는 회귀 시험 1건.
- 실제 검색 4개가 동시에 Barrier에 도달해야 통과하며 합류·추출을 한 번만 수행하는 시험 1건. 시간 단축률을 측정하는 시험은 아니다.
- 빈 검색 결과와 note/stop 정책, stance 분리 on/off 조합 4건.
- con 검색 예외가 원래 RuntimeError로 전파되고 합류·추출·작성에 도달하지 않는지 순차/병렬 각 1건. Runner도 결과 대신 예외를 낸다.
- 같은 source_id에 갈래별 다른 본문이 와도 sources 리듀서에서 base 본문 하나만 남는 시험 1건.

전체 시험 실행 시도:

```powershell
python -m pytest -q -p no:cacheprovider --basetemp=.runs/r6/full-tmp --junitxml=.runs/r6/full-pytest.xml
```

**tests not run here: Python is not available on PATH.**

이 환경에서 시험 미실행: Python 명령이 `CommandNotFoundException`으로 시작되지 않는다. `python`, `python3`, `py`, `pytest` 실행기가 PATH에 없고 저장소의 `.venv-python`·`.venv-cache`에도 `Scripts/python.exe`가 없다. 실행 0건이며 passed/failed/error/skipped는 집계 불가다. 새 21건과 기존 전체 시험의 통과 여부는 **미검증**이며 NightCoder 게이트에서 판정해야 한다. 실행 시도 기록은 `.runs/r6/test-attempt.txt`에 둔다.

## 병렬로 얻는 것·잃는 것

- 얻는 것: 독립 검색을 겹쳐 실행할 수 있다. 합류 후 순서를 고정하여 완료 순서에 따른 보고서 변화를 방지한다. 네 갈래의 검색 지연이 비슷하고 저장소가 동시 읽기를 지원하면 대기 시간 감소를 기대할 수 있다. 실제 지연 개선은 미검증이다.
- 잃는 것: 앞 갈래에서 얻은 수를 모르므로 후보를 더 읽을 수 있다. 네 갈래 후보 요청량의 합은 최대 10k이며, 순차는 앞 갈래가 비었을 때 4k까지 줄어든다. 검색 호출 수는 양쪽 모두 네 번이다. 합류 노드 한 단계와 후보 상태 메모리가 추가된다. 기본 shadow cost는 모델 토큰 추정치이므로 검색 지연·후보 읽기 비용을 표현하지 않는다.
- 예외: 현재 구현은 한 갈래 실패를 삼키거나 부분 보고서로 바꾸지 않는다. 순차는 실패 지점 뒤 검색을 시작하지 않지만 병렬은 다른 검색이 이미 실행 중이거나 끝났을 수 있다. 다른 갈래의 부수 효과 롤백·즉시 취소는 보장하지 않는다. 예외 전파 동작을 시험으로 작성했으나 실행 확인은 미검증이다.

## 고치지 않은 것과 이유 / 미검증

실제 Chroma 동시 검색의 안전성·성능, 모델 품질은 미검증이다. 이 옵션은 기존 주입형 SearchFn을 사용하며 저장소를 새로 구현하거나 memvid를 연결하지 않는다. 실제 저장소 어댑터에서 병렬 옵션을 노출하는 서비스·CLI 변경은 허용 파일 범위 밖이므로 후속 연결 필요다. 네트워크·모델 다운로드·LLM 호출·패키지 설치는 수행하지 않았다. 실제 모델 실행은 이번 작업에서 금지되어 모델 실행 명령도 추가하지 않았다.

기존 시험·기대값·skip·KNOWN_DEBT와 금지 파일을 수정하지 않았다. 초기 git status는 깨끗했다. 보호 파일 18개는 `.runs/n10/protected-after.json`의 Expected SHA-256과 작업 전 18/18 동일했다. 최종 대조와 커밋 상태는 아래에 기록한다.

## 최종 확인·커밋 제약

보호 파일은 작업 후에도 18/18 SHA-256 동일하다. 증거는 `.runs/r6/protected-before.json`, `.runs/r6/protected-after.json`이다. `git diff --check`를 통과했고 신규 시험·보고서의 줄 끝 공백도 별도로 확인했다. 변경은 지정 소스 1개, 신규 시험 1개, 본 보고서 1개뿐이다.

현재 브랜치 `nc/rra-codex`에서 세 파일을 `git add -- ...`로 스테이징하려 했으나 `fatal: Unable to create 'C:/work/rra-codex/.git/index.lock': Permission denied`로 실패했다. 이 샌드박스의 `.git`은 읽기 전용이며 권한 상승이 허용되지 않는다. 따라서 커밋 해시는 없으며 미커밋 변경 0건 조건은 달성하지 못했다. 작업을 지우지 않고 세 파일을 보존한다. Git 쓰기가 가능한 NightCoder 환경에서 이 세 파일을 단일 커밋으로 수집해야 한다. push·원격·브랜치 설정 변경은 하지 않았다.
